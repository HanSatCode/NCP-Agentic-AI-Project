# 파일 버전 정리 — 규칙·예시 파일·QA

기준은 저장소의 `CLAUDE.md`와 `docs/spec.md`다. 이 스킬은 규칙을 새로 정하지 않는다. CLAUDE.md에 없거나 애매한 것은 "확인 필요"로 적고 넘어가며, CLAUDE.md와 다른 것을 발견하면 멈추고 알린다.

## 어떤 작업을 할지 고르기
요청에 맞는 절 하나만 하면 된다. "QA 해줘"처럼 범위가 없으면 4절 전체 QA를 한다.

| 요청 | 할 일 | CLAUDE.md의 옛 이름 |
|---|---|---|
| 규칙 보여줘 · 키워드/점수 바꿔줘 | 1절 규칙 | `/version-rules` |
| 예시 파일 만들어줘 · F-01-03 준비 | 2절 예시 파일 | `/make-samples` |
| 기능 하나 고친 직후 확인 · 결과 확인 | 3절 빠른 확인 | `/check-result` |
| QA · 테스트 · 배포 전 점검 | 4절 전체 QA | — |

스크립트는 모두 TypeScript이고 Node 22.18 이상이 그대로 실행한다 (빌드·추가 설치 없음). 분석 함수는 `src/analysis/`에서 직접 불러온다.
| 명령 | 파일 | 하는 일 |
|---|---|---|
| `npm run samples` | `scripts/make-samples.ts` | `public/samples/manifest.json`에 적힌 demo·edge 파일을 만들고 수정 날짜를 맞춤. 같은 입력이면 같은 바이트 |
| `npm run check` | `scripts/check-result.ts` | demo·edge 파일로 분석·이름 변경 결과를 `public/samples/expected.json`과 비교 |
| `npm run qa` | `scripts/qa.ts` | 규칙 검사 + 단위(기본 이름) + 시나리오(E06~E18 등) + 불변식(fuzz). 케이스는 메모리 안에서 만듦. `SEED=42`로 seed 지정 |
| `npm test` | `src/**/*.test.ts` | 함수별 단위 테스트 (`node --test`) |

## 0. 공통 — 시작 전에
| 확인할 것 | 어떻게 | 비어 있으면 |
|---|---|---|
| `git pull` | | |
| 기술 스택·로컬 실행 방법 | CLAUDE.md "기술 스택·실행" 표 | 임의로 정하지 말고 물어본다 |
| 분석 함수 위치·이름·입력 | `src/analysis/`를 읽는다 (`analyze`, `rename`, `parseName`, `findDuplicates`, `acceptFiles`, `makeDownload`, 입력 타입 `InputFile`) | 물어본다 |
| D-19(있으면 좋은 기능) | 결정 사항 표 | "보류"면 메타데이터 케이스는 SKIP |
| D-18(F-02-06 미루기) | 결정 사항 표 | 확정: 미루지 않음. 중복 케이스는 SKIP 없이 검사한다 |
| 의존성 | `node_modules`가 없으면 `npm install` | |

공통 규칙:
- **원본은 덮어쓰지 않는다.** `public/samples/manifest.json`·`expected.json`과 demo·edge 파일 목록은 바꾸기 전에 사용자에게 묻는다
- **가명·예시 데이터만 쓴다.** 메타데이터 작성자도 가명 (D-16)
- **기대 결과는 사람이 CLAUDE.md 규칙 표를 적용해 적는다. 분석 코드로 계산하지 않는다.** 같은 버그가 코드와 기대값에 함께 들어가면 테스트가 통과해 버린다
- **수정 날짜는 항상 manifest 값을 쓴다.** git은 수정 날짜를 저장하지 않는다 (D-14)
- **틀려도 바로 고치지 않는다.** 원인과 고칠 방법을 먼저 설명하고 승인받은 뒤 고친다

## 1. 규칙 — `rules/version-rules.json`
CLAUDE.md: "키워드와 점수는 코드에 직접 쓰지 않고 `rules/version-rules.json`에서 읽는다." 이 파일은 CLAUDE.md를 옮긴 것이고, CLAUDE.md가 기준이다.

| 키 | 내용 | 출처 |
|---|---|---|
| `keywords` | 진짜최종·찐최종 40 / 최종수정 30 / 최종·final·완성·제출 20 / 수정 10. 뒤에 "본"이 붙은 형태도 같은 점수 | D-01, D-26 |
| `copyMarks` | 이름 끝의 `(1)`, `_1`(1~2자리), `복사본`, `- 복사본`, `copy` | D-02 |
| `dates` | `2026-11-20`, `20261120`, `1120`, `11.20` (월·일로 읽힐 때만 날짜) | D-03 |
| `version` | `v2`, `V2`, `ver2` (대소문자 무시, 앞에 영문자가 붙으면 아님: `server3`) | 버전 판정 규칙 |
| `separators` | 공백·`_`·`-`·괄호 | 기본 이름 5단계 |

코드에 있는 값 (규칙 파일 밖):
| 값 | 위치 |
|---|---|
| 판정 순서 (버전 → 날짜 → 키워드 → 수정 날짜), 1위 동점·2위 이하 동점 | `src/analysis/analyze.ts` `CRITERIA`, `rank` |
| 추천 이유 문구 틀 | `analyze.ts` `reasonText` |
| 20MB, 같은 파일 판정 | `src/analysis/upload.ts` `MAX_SIZE`, `fileKey` |
| 새 이름 형식, 충돌 `_2`, 금지 문자 → `_` | `src/analysis/rename.ts` |
| zip 이름 | `src/analysis/zip.ts` |

정규식은 JavaScript 문법이고 `u` 플래그로 컴파일된다 (이름 있는 그룹 `(?<m>…)`, 뒤보기 `(?<!…)` 사용 가능).

**보여주기**: 위 표 형태로 현재 값을 보여준다.

**검사하기** (규칙을 쓰는 작업 전에 항상): `npm run qa`의 "규칙" 단계 (키워드·점수가 CLAUDE.md와 같은지, 정규식이 컴파일되는지).

**고치기** — 규칙을 바꾸는 것은 CLAUDE.md를 바꾸는 것이다.
1. 바꾸려는 값이 CLAUDE.md와 다르면 멈추고 무엇이 다른지 알린다
2. 사용자가 확정하면 세 곳을 함께 고친다: `rules/version-rules.json`, CLAUDE.md의 해당 표·결정 사항(새 D-xx는 "추천안"), `scripts/qa.ts`의 규칙 대조 값과 단위 표(새 예시 1개 이상)
3. 키워드 추가 시: 기존 키워드를 품는지("완전최종" ⊃ "최종"), 흔한 단어와 겹치는지("수정본"), 영문 대소문자
4. `npm run qa` → 3절 빠른 확인. 기대 결과가 바뀌면 `public/samples/expected.json`도 사람이 고친다
5. commit 예: `F-02-03 키워드 '완전최종' 40점 추가`

## 2. 예시 파일 — `public/samples/`
```bash
npm run samples
```
- 만들 파일과 수정 날짜는 `public/samples/manifest.json`, 파일별 본문은 `scripts/make-samples.ts`의 `CONTENT`에 있다. 바이트가 같은 사본은 `{ copyOf: "..." }`
- docx·pptx·xlsx는 `fflate`로 실제로 열리는 문서를 만든다. hwp는 실제 형식으로 만들 수 없어 이름·날짜 판정용 텍스트 파일이다
- 같은 입력이면 항상 같은 바이트라서 다시 돌려도 git 변경이 생기지 않는다

### demo (시연용 8개)
| 파일 | 역할 |
|---|---|
| 발표자료_진짜최종.pptx | 최신 후보 (키워드 40) → v4 |
| 발표자료 최종수정.pptx | 키워드 30 → v3 |
| 발표자료_최종.pptx | 키워드 20 → v2 |
| 발표자료(1).pptx | 복사본 표시, 0 → v1 |
| 보고서_v3.docx | 최신 후보 (v3) → v2 (D-13) |
| 보고서_v3 복사본.docx | 보고서_v3.docx와 바이트 동일 → 중복 (D-15) |
| 보고서_v2.docx | v2 → v1 |
| 회의록_1115.docx | 단독 파일 → v1 |

수정 날짜는 manifest에 있다. 표에 다시 적지 않는다.

### edge (CLAUDE.md "테스트용 애매한 경우")
| 파일 | 확인할 것 |
|---|---|
| 기획서_최종_수정.docx, 기획서_최종.docx | "최종_수정" 30점으로 1위 (D-01) |
| 회의록.hwp, 회의록(1).hwp | 같은 그룹, 수정 날짜로 1위 + 주의 문구 (D-02, D-05) |
| 메모_최종.txt, 메모-최종.txt (수정 날짜 같음) | 확인 필요, STEP 3 막힘 (F-02-04, D-08) |
| 실험_1350.docx | 1350을 날짜로 보지 않음 (D-03) |
| 자료_v2.pdf, 자료_v2 - 복사본.pdf (바이트 동일) | 복사본 표시 쪽이 중복 (D-02, D-04) |

### manifest.json · expected.json
- `manifest.json`: `"demo/파일명": { "lastModified": "2026-11-20T23:40:00+09:00", "author": "가명" }`. 키 순서가 목록 순서
- `expected.json`: `scenarios[]`. 시나리오마다 한 번에 올린 파일 묶음(batch 1)이고 `files` 순서가 목록 순서
  - 파일: `path`, `baseName`, `duplicateOf`(남길 파일 이름), `newName`(`null` = 중복 제외 또는 아직 안 고른 "확인 필요")
  - 시나리오: `groups[]`(`baseName`, `status`, `latest`, `reason`), `singles`, `summary`, `blockedGroups`
  - 적지 않은 칸은 검사하지 않는다

### F-01-03에서 불러오기 (브라우저)
`src/analysis/upload.ts`의 `loadSamples()`가 manifest를 읽어 수정 날짜를 넣은 `File`을 돌려준다. 화면은 기존 목록이 있으면 비울지 먼저 묻고, `acceptFiles` → `toInputFiles`로 F-01-01과 같은 경로로 추가한다.

끌어다 놓기 시연용 실제 파일은 시연 PC에서 `npm run samples`를 다시 돌려 날짜를 맞춘다. 시연 전에 탐색기에서 수정 날짜를 확인한다.

파일·날짜를 바꾸면 `manifest.json`, `make-samples.ts`의 `CONTENT`, `expected.json`을 함께 고친다. CLAUDE.md "판정 예시"와 다르면 멈추고 알린다.

## 3. 빠른 확인 — 기능 하나 고친 직후
CLAUDE.md 작업 규칙: "분석·이름 변경 기능을 만들거나 고친 뒤에는 확인한다." 1~2분 안에 끝나는 검사다.

```bash
npm run check && npm test && npx tsc --noEmit
```
1. 예시 파일이 없다고 나오면 `npm run samples`부터
2. 분석 코드를 훑어 아래를 보고한다
   - 키워드·점수가 코드에 직접 적혀 있음 (규칙 파일에서 읽어야 함)
   - `document`·`window` 사용 (화면 코드와 섞지 않음)
   - `crypto.subtle` 사용 (http 배포 주소에서 안 됨. 크기가 같은 파일끼리 바이트 직접 비교, D-17)
   ```bash
   grep -rnE "crypto\.subtle|document\.|window\." src/analysis
   ```
3. 비교 규칙 (`check-result.ts`가 이미 이렇게 한다)
   - `expected.json`에 적힌 항목만 비교, 문구(추천 이유)는 글자 그대로
   - 새 이름 날짜는 실행하는 PC 시간대 기준 YYYYMMDD. 다르면 시간대 문제로 보고 (KST 기준)
   - 아직 안 만든 기능은 SKIP. 단, 우선순위 "상" 기능이 없으면 FAIL
4. 결과를 표로 보여주고(형식은 5절), 브라우저에서 확인할 방법을 한 줄로 알려준다
   (예: "[예시 파일로 해보기] → [분석하기] → 보고서 카드에 중복 배지")

## 4. 전체 QA
순서: 빠른 확인(3절) → `npm run qa`(규칙·단위·시나리오·불변식) → `npx next build` → 화면 → http → 보고서

```bash
npm run qa              # seed 42
SEED=7 npm run qa       # 다른 무작위 세트
```
FAIL이 하나라도 있으면 종료 코드 1. 출력은 PASS가 아닌 것만 보여주고 마지막에 단계별 개수를 적는다.

### 4-1. 테스트 케이스 (`scripts/qa.ts`)

### 4-3. 불변식 검사 — 무작위 파일명
seed로 무작위 파일명 세트 300개를 만들어(기본 이름 + 서로 다른 종류의 꾸밈 2개 + 복사본 표시, 15%는 바이트 같은 사본) I1~I10을 확인한다.
- I1 새 이름 형식 `기본이름_v번호_YYYYMMDD(_k).확장자`, 금지 문자 없음
- I2 그룹마다 번호 1..k 빠짐없이 한 번씩 (중복 제외)
- I3 최신 후보가 가장 큰 번호 · I4 확인 필요 그룹은 선택 없음
- I5 입력 순서를 3번 섞어도 그룹·최신 후보 같음 (1위 동점 그룹의 최신 후보, 바이트가 같은 파일은 D-04상 순서에 따라 중복 쪽이 바뀌어 그룹·단독 자리도 바뀔 수 있으므로 제외) · I6 두 번 돌려도 같음
- I7 새 이름끼리 안 겹침 · I8 꾸밈만 다른 파일은 같은 그룹 · I9 중복은 번호·내려받기 없음
- I10 추천 이유가 문구 틀 6개 중 하나

실패하면 파일을 하나씩 빼며 **가장 작은 실패 세트**로 줄이고, 시나리오 블록으로 추가하자고 제안한다(기대 결과는 사람이 적는다). seed를 보고서에 적는다. 생성기가 만든 비현실적인 이름(날짜 2개 등) 때문이면 생성기를 고친다.

### 4-4. 화면 검사
UI가 있으면 로컬 실행 방법(`npm run dev`)으로 띄워 브라우저(Claude in Chrome 등)로 확인한다. 수정 날짜가 manifest 값이 되도록 파일은 페이지 안에서 `File`로 만들어 넣는다.
```js
const dt = new DataTransfer();
for (const f of files) dt.items.add(new File([new Uint8Array(f.bytes)], f.name, { lastModified: f.lastModified }));
const input = document.querySelector('input[type=file]');
input.files = dt.files; input.dispatchEvent(new Event('change', { bubbles: true }));
// 끌어다 놓기(F-01-02): 드롭 영역에 new DragEvent('drop', { dataTransfer: dt })
```
| 영역 | 확인할 것 |
|---|---|
| 화면 상태 | 처음(M-01, [분석하기] 비활성) → 1개(M-02) → 2개 이상(활성) → 분석 중 → ② → ③ |
| 안내 문구 | M-01~M-08 글자 그대로. M-04는 같은 파일 두 번, M-07은 폴더 드롭 |
| 배지 | 4개만, 색과 글자 함께 (최신 후보 초록 / 확인 필요 노랑 / 중복 회색 / 직접 선택 파랑) |
| 직접 선택 | 라디오 변경 → "직접 선택" 배지, 고른 파일이 가장 큰 번호 (D-09) |
| STEP 3 | 기본 이름 수정이 미리보기에 바로 반영, 비우면 M-06 후 되돌림, 겹침 `_2`, 금지 문자 `_` |
| 다시 계산 | 분석 후 추가·빼기 → 다시 계산, 직접 선택 초기화 (D-12). 1개가 되면 결과 숨기고 M-02 (D-07) |
| 내려받기 | 1개면 단일 파일, 2개 이상이면 `정리된파일_YYYYMMDD.zip`. zip 안 이름이 미리보기와 같은지, 중복 없음, 0개면 비활성, M-08 |
| 카드 접기 | 4개 이상이면 2개 + "… N개 더", 누르면 펼침 |
| 폰 | 480px 이하에서 카드 한 줄에 하나, 목록 표는 파일명·수정 날짜만 |
| 원본 보존 | 올린 파일과 내려받은 파일의 바이트가 같고 이름만 다름 |
| 예시 파일 | [예시 파일로 해보기] → 8개가 manifest 날짜로 들어오는지, 기존 목록이 있으면 확인을 묻는지 |

UI가 없으면 "상" 기능이 화면에 없는 것이므로 FAIL로 적고 어떤 함수가 준비돼 있는지 함께 적는다.

### 4-5. http 주소 검사 (꼭 한다)
배포 주소는 https가 아니라서 `crypto.subtle`이 없다. localhost는 안전한 주소로 취급되므로 통과해도 믿지 않는다.
- `npm run dev -- -H 0.0.0.0`으로 띄우고 `http://<사설 IP>:3000`으로 열어 `window.isSecureContext === false`인지 먼저 확인
- 그 상태에서 중복 케이스(edge 자료_v2, E14, E15)를 다시 돌린다
- 배포 주소에서도 같은 검사. 서버로 파일이 올라가는 요청이 없는지 네트워크 기록으로 확인 (D-17)

## 5. 판정과 보고
| 결과 | 뜻 |
|---|---|
| PASS | 기대 결과와 같음 |
| FAIL | 다름. 실제·기대 값과 기능 ID를 적는다 |
| SKIP | 조건이 안 됨 (D-19 보류, 기능 미구현). 이유를 적는다 |
| 확인 필요 | CLAUDE.md만으로 정답을 정할 수 없음. 팀이 정할 질문을 한 줄로 |

- FAIL이면 원인과 고칠 방법을 먼저 설명하고 승인받은 뒤 고친다. 고친 뒤 다시 돌린다
- 기대 결과가 CLAUDE.md와 다르다고 판단되면 코드를 맞추지 말고 멈추고 알린다
- "보류" 결정(D-05 등)은 명세서대로 동작하는 것을 정답으로 본다
- "있으면 좋은 기능" 작업 중 필수 기능(상)이 깨지면 직전 커밋으로 되돌리자고 제안한다

보고서는 `output/qa-report-YYYYMMDD-HHMM.md`(빠른 확인은 `output/check-result-YYYYMMDD-HHMM.md`)에 새 파일로 쓴다. 결론을 맨 위에 둔다.

| 단계 | PASS | FAIL | SKIP | 확인 필요 |
|---|---|---|---|---|
| 규칙 · 빠른 확인 · 단위 · 시나리오 · 불변식 · 화면 · http | | | | |

## FAIL
| 케이스 | 기능 | 기대 | 실제 | 추정 원인 |

## 확인 필요 (팀이 정할 것)
| 케이스 | 질문 |
